# Local team-chat voice prototype

Push-to-talk records at most 29 seconds. LFM3 Audio transcribes locally; the browser posts the resulting text through the normal team-chat message path. The selected chat assistant answers using its usual permissions and tools, and LFM3 Audio reads the saved reply aloud. This is a turn-based speech → text → chat → speech pipeline, not a low-latency streaming speech-to-speech model. Both sides of the conversation are ordinary saved text messages. Voice on a shared channel follows the existing private-answer routing; business answers are not exposed to the rest of a channel. A Listen action allows replay when the browser blocks automatic playback.

The speech worker is loopback-only and requires a random token. It accepts audio bytes and saved-message text, with a single concurrent request, bounded recording size/duration, private temporary files, process deadlines, and no speech logging. `TeamChatController` enforces normal access and room visibility; speaking uses a visible, completed assistant message ID, not caller-supplied text. The client accepts only a loopback HTTP endpoint. Browser microphone access requires a secure origin and user permission. The worker uses an LFM3-compatible `llama-mtmd-cli`, `llama-tts` and ffmpeg. It must be resource-tested alongside the model gateway before production use.

Installation is not automatic. The unit is intended for an unprivileged host user; `%h/.config/rupert/voice-worker.env` supplies `VOICE_MODEL`, `VOICE_PROJECTOR`, `VOICE_MTMD`, `VOICE_TTS`, and `VOICE_TOKEN_FILE`. The token file must be mode 0600 and contain at least 32 random characters. A container-bound Incus proxy can expose host loopback port 18082 only to the Rupert container. `RUPERT_VOICE_URL=http://127.0.0.1:18082` and the same `RUPERT_VOICE_TOKEN` must be set in Rupert's protected runtime environment. Keep the token and environment out of the repository and logs. The app hides voice controls until configured. Avoid starting multiple copies or competing with the serialized production model gateway. Validate the browser, microphone, authenticated access, private-room routing, saved transcripts, playback, load and recovery before enabling for users.

## Isolated validation

On 2026-10-27, the worker transcribed a synthetic WAV and generated a valid WAV reply using the LFM3 Audio Q4_K_M model. An isolated Rails integration test then used the real local worker and the configured cloud assistant: it posted the transcription into a private test chat, ran the assistant reply job, verified both text messages persisted, and synthesized the saved assistant response. Unauthorized worker access returned HTTP 401. The test used no real business data. Browser microphone permissions, playback, deployment, sustained load, and shared-channel-to-private-room navigation remain unverified.

A headless Firefox test also used a prerecorded WAV in place of the microphone and a simulated audio player. It exercised the real browser recording control, transcription request, saved private-chat message, real assistant job, speech request, and automatic playback trigger. This does not establish hardware microphone access or audible playback on a user's device.

The shared admin-room handoff was subsequently tested through the real local speech worker and a real cloud assistant on synthetic data. The integration test recorded the transcription in the channel, verified the corresponding private user message and assistant reply, resolved the handoff as the requester, and generated a WAV from the saved private answer. It passed 10 assertions. The new handoff's browser playback and physical microphone remain to be verified, and this prototype is not deployed.
