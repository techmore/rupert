# Team chat benchmark review — 2026-10-27

This review covers the built-in 21 general, 35 finance and 10 cross-area questions, the 2,500-question bank, the grader and available October 22 run reports. Counts refer to the built-in files; workspace edits can change the evaluated set. No production business figures or model answers are reproduced here.

## Findings

1. **Moving reference data:** each answer is graded against tool calls made afterwards. Results can change during or between model runs (especially today, queues and alerts), so a score difference is not necessarily a model difference. Preserve a read-only, tenant-scoped fixture snapshot and frozen evaluation date for each comparison cohort. Record the fixture fingerprint, question-set fingerprint, runtime, model, quantization and grader revision with every run.
2. **Missing evidence:** a missing reference tool or a tool error was sent to the judge as ordinary text, and questions without checks could be graded without evidence or an authored expectation. Such cases must be ungraded and counted, not converted into model scores. This change adds that guard and shows graded and ungraded counts. It does not establish that a successful tool returned all needed fields: run `team_chat:battery_coverage` on a non-production fixture first.
3. **No fixed gold standard for many questions:** 18/21 general and 9/35 finance questions have no authored expectation; the general navigation question has neither a reference check nor an expectation. All 10 cross questions have an expectation. Add concrete, independently reviewed requirements and explicit permissible unknowns for each task. Judge statements only when the reference supports them; distinguish omitted evidence from contradictions.
4. **Grading failures change the denominator:** historical runs include ungraded answers. A mean of graded answers alone can look better when hard questions fail to grade. Always report graded/total, answer failures, tool failures and ungraded counts by category, with a separate comparable score on the same successfully graded cases. The guard in this change surfaces the denominator in run summaries.
5. **Bank is not itself a model benchmark:** its 2,500 entries are routing/coverage checks, originally with 1,173 yes, 706 partial and 621 no labels; two corrections now leave 1,171 yes, 708 partial and 621 no. Twelve normalized question strings are repeated. The graded bank sample defaults to five answerable and one unanswerable per area; tools with required parameters are excluded from reference checks. Review duplicate intent and labels, provide valid tool arguments and reference fields, and do not treat an ungrounded sample as an accuracy score.
6. **Judge and prompts:** one cloud model supplies subjective 1–5 ratings; the references and answers are truncated. Judge configuration, reference truncation, absent citations, and model-specific tool access or inference settings can skew results. Freeze the judge, rubric and inference budget; run a blinded human review of a stratified sample, and report disagreements. Model response and tool traces remain private.
7. **Audio and vision:** text-only business questions cannot evaluate transcription, speech generation, audio-to-audio behavior or image interpretation. Add separately scored, consented fixtures with exact transcripts, spoken-response text and playable output, noisy audio, image cases and latency. Do not combine those scores with text/tool grades.

## Comparable rerun protocol

Create a versioned fixture, answer key and category matrix; separately evaluate accuracy, groundedness, correct refusal, tool use, task completion and latency. Include common owner questions, real held-out cases, edge cases, and destructive-request proposal boundaries. Deduplicate or intentionally label paraphrases, set fixed seeds, and pin all inputs and outputs. Run reference coverage before models, then a small compatibility pilot with actual tool calls for each candidate. Run the same frozen cohort against Qwen, DeepSeek and all relevant LFM3 variants, save every question/answer/trace/grade and failure, and report per-category results, graded denominators and paired differences rather than only a mean. Gemma was removed from the remaining queue at the owner's request; its historical evidence is retained. Audio and image cases require their own integration and harness. Do not start the full production-data run until these safeguards and fixture coverage exist.

The change in this worktree is a first scoring safeguard, not the completed revamp. It has not established frozen reference fixtures, audited all 2,500 labels, benchmarked models, or validated voice mode.

## Implementation in progress

A comparison cohort captures each question's redacted reference in an encrypted, mode-0600 file bound to its tenant, requester, date and question definition. During grading, a missing/changed question, date, or reference becomes ungraded; comparison is paired by question ID and reports the number of comparable grades, wins, ties and losses. The current implementation rechecks evidence after the answer and is deliberately fail-closed: it does not freeze the data a model sees during inference. For a rigorous comparison use identical, isolated database fixtures and a controlled date, not live business data. The encrypted cohort is sensitive; keep its encryption configuration and recovery key outside the report.

A static review found two duplicate questions with conflicting answerability labels: `receipts to review` and `sales per labor hour this week`. The bank now marks both duplicates partial, reflecting count-only receipt information and the absence of a precomputed combined sales/labor metric. This is a conservative label, not proof that all other entries are correct.

To capture a cohort, with a pre-created private parent directory and an active administrator, run `bin/rails team_chat:battery_cohort BATTERY=finance COHORT=/private/new-file`. Use the same `BATTERY`, requester, workspace and `COHORT` for each `team_chat:battery` run; each full run is saved under a cohort-specific set name. `team_chat:battery_compare BASELINE=<run_key> CANDIDATE=<run_key>` reports paired aggregate differences and question IDs. These commands do not create a common application fixture or automatically provision model servers; those remain required before a trustworthy rerun. Voice and image tasks remain outside this text/tool harness.

## Synthetic pilot review

A one-question Qwen pilot exposed a judge error: the reference said there were no paid orders **stored**, with empty per-source sales arrays, while the judge treated this as proven zero activity and graded the model's caution as a refusal. The original pilot grade remains in its private fixture database but is invalidated for comparisons. The rubric now distinguishes absent evidence from proven zero and an evidence-based limitation from an unjustified refusal. A human review is still needed: prompt changes alone do not validate a judge.

That same reference showed ISO dates replaced by `[phone]`. The redactor now preserves exact, valid ISO calendar dates while still masking phone numbers; this change is separately tested. Comparisons must use newly captured cohorts because the reference and rubric changed.

LFM3 text produced a structured call in a small synthetic compatibility check but reached the twelve-step tool limit for the first fixture question in both its default and bounded-thinking profiles. The unbounded pilot's second question was manually interrupted; it is not a valid model failure. These isolated CPU pilots are diagnostics, not a leaderboard or a substitute for full battery results.

`ruby web/script/audit_team_chat_questions.rb` performs a repeatable static inventory: all 2,500 IDs are unique, 12 normalized question texts repeat, and after the two label corrections no exact duplicate has conflicting answerability. This is a structural audit, not human validation of every label. The 21/35/10 fixed questions now all have either reference checks or an authored expectation; 17 general and 9 finance questions still lack specific authored expectations, so the need for rubric review remains. A fixture capture using the default 54-question bank sample had 18 cases without usable evidence; those must remain ungraded until individually repaired.

A registry cross-check found 42 distinct tool names in the bank: 40 MCP tools and two built-in lookup tools (`search` and `system_status`). Of 2,500 questions, 529 list no tools; none of those is labeled fully answerable. Every partial or unanswerable entry has a stated gap. This establishes basic structural consistency, not that the labels, gaps, tool arguments, or expected answers are correct.

Navigation questions in the graded bank now obtain evidence from the asking person's read-only `where_is`/`how_do_i` lookup, using the question as the lookup argument. Missing lookup results still fail closed, and arguments for financial tools are not guessed. In the synthetic fixture, this reduced the default 54-question bank sample from 18 to 9 questions without usable evidence. The remaining cases require authored expectations or verified arguments.

The nine unresolved cases were identified by ID. Three ask to create or reassign a task (`daily-161`, `team-192`, `work-074`); they now have authored expectations requiring a reviewable proposal or clarification and prohibiting a claim that an unapproved action succeeded. This assesses the answer text, not proof of the action-card state or absence of side effects; those need separate instrumentation. Two refund-rate questions (`bookkeeping-187`, `cross-160`) now have explicit metric and period arguments, and `daily-042` now uses the register-specific daily-close reference rather than the order metric. A fresh capture on the synthetic fixture finds 3 of 54 still ungradable: the system questions `system-042`, `system-183`, and `system-178` rely on unavailable or failing fixture references. These changes require a new cohort and are not retroactively applied to the running comparison.

Future battery rows also preserve the names of action tools proposed before the test dismisses them. This makes the existence of a proposal auditable without copying its arguments into the scorecard. The grader still evaluates answer text and reference evidence; action correctness and absence of side effects require independent checks and are not implied by the grade.

The missing system references are a permissions and fixture issue, not evidence that a model answered incorrectly. `deploy_status` requires an instance operator and the `ai_health` tool is available only to super administrators. The synthetic requester cannot access the latter. The former returned a wrapped reference error; its precise cause needs further investigation. A further complication is that “which AI model is Rupert using” can have a different correct answer for each candidate, so a single model-independent answer key is inappropriate. Resolve these with a separately permissioned, synthetic system fixture and explicit per-model expectations; do not grant the regular fixture user live operator access or invent a status.

This permission issue extends beyond the three sampled questions. A static inventory of the 2,500 bank entries found 46 that name at least one of `ai_health` (10), `deploy_status` (18), or `backup_freshness` (18); 30 of those tool mentions are on entries labeled fully answerable. `ai_health` requires a super administrator; deploy and backup status require an instance operator or an isolated workspace, in addition to normal tool availability and scope. These counts describe declared tools, not how many questions actually fail for a particular user. The global yes/partial/no label does not encode requester permissions. A revamped battery should specify the requester's role, workspace mode and granted scopes, capture reference evidence under that identity, and evaluate a permission-limited answer against those conditions. An unavailable tool must not silently become a reference or justify granting extra access.

A paired one-question pilot with six synthetic orders scored Qwen 3.5 4B and LFM3 Text 4/5 each; both outputs were judged too dump-like. It used a single CPU server in each case, so its timings do not represent the existing Vulkan production gateway. The question, answers, grader notes, execution records and cohort are preserved in the private fixture database and encrypted cohort copy; one question cannot support a ranking.

## Synthetic queue started

A CPU-only evaluation queue was started on 2026-10-27 with the synthetic fixture, one model server at a time. It asks the fixed general (21), finance (35), cross (10) and deterministic bank sample (54) of Qwen 3.5 4B, Gemma 4 E4B, LFM3 Text, VL, Audio, Omni, and Rupert. The bank cohort has nine questions without usable reference evidence; they remain ungraded. A per-set advancing simulated clock keeps deadlines working, while reference retrieval uses the same fixed evaluation instant. The models are tested through the text/tool workflow; no claim is made about image or speech quality. The CPU settings differ from the live Vulkan service, so speed comparisons are specific to this experiment. Results, private fixture databases, captures and the exact source changes are saved outside the repository under `~/models-lfm3/benchmark-evidence/full-20261027/`. This is a long-running task, not a completed comparison.

That initial CPU queue was stopped and preserved when the owner required a 120-second per-answer deadline. The replacement queue uses the same isolated synthetic fixture and question cohorts, scores an answer timeout as 1/5, and uses a new Vulkan-enabled llama.cpp build for the local models. Qwen loaded 33/33 layers and LFM3 Text loaded 25/25 on the Radeon 780M. DeepSeek runs through its configured cloud provider; DeepSeek also acts as judge, a potential source of bias. The local queue runs the first set across models before proceeding to the next set. The new run's evidence and database snapshots are stored locally under `~/models-lfm3/benchmark-evidence/limited-20261027/`. Earlier copies were sent to the NAS before the owner clarified that benchmark evidence belongs locally; benchmark copying to the NAS has been stopped. The older partial CPU scores are not part of the new comparison. This run remains in progress.

During LFM3 Text's first set, three failed replies reached the 12-step limit after six tool calls each. Two cases did not repeat identical tool arguments; one repeated an identical call twice. The problem is therefore not uniformly an exact-call loop. Preserve these failures under the frozen setup and evaluate any prompt, tool selection, or step-budget changes in a separately identified experiment rather than changing the active comparison.

In the first three Omni responses, no tool calls were executed. One response emitted repeated placeholder-like text, one refused, and one asserted an order that the reference does not contain; two included a literal `</think>` marker. The Vulkan server's startup log reports template thinking enabled even though the queue sets a zero reasoning budget and requests disabled thinking. Source inspection shows that this startup message is calculated from template support and the `--reasoning` flag; request processing separately applies the `enable_thinking` template argument. Thus the startup message alone does not establish the setting used for each request or the cause of Omni's behavior. A separate controlled template and tool-call compatibility test is needed before treating the results as the model's intrinsic capability.

The running reports' “Number check ... 0 of N answers” line counts explicit flags, not a complete verification of all figures. Some responses fail or have no tool evidence, and financial responses use a different evidence path. Do not interpret zero flags as proof that all numeric claims are supported. Future summaries state this limitation explicitly; the active frozen run keeps its original wording.

The frozen general cohort's `c2` reference lacked the specific timesheet-approval row. `compliance_check` can provide it, but its default omits healthy items; generic `items[].title` and `items[].status` needs incorrectly accepted unrelated compliance rows. The original `c2` grades are therefore not reliable. A separate saved analysis excludes `c2` for every model without modifying the original reports. For a future cohort, `c2` and the Drive-retention question request healthy items, select the named row, and require that row's relevant fields. A fresh synthetic capture with those checks found 0 ungradable among the 21 general questions; this is a reference-coverage result, not validation of every grading decision.
